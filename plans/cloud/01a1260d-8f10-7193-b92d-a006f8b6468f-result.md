## Summary

New package `@nera-static/starter-blog` 1.0.0: a blog starter on `@nera-static/theme-blog`
with the eight plugins (tags, page-pagination, feed, sitemap, code-blocks, navigation,
images, social-media-links). It ships `config/` (app + six plugin/theme configs),
`theme/views/partials/` (nine seam overrides), `theme/views/vendor/` (the published plugin
templates), `pages/` (home, archive, about, imprint/privacy placeholders, three posts over
2025–2026) and one sample image. It also adds tests (contract + end-to-end scaffold), the
README, the CHANGELOG, CI, lint and hooks. A scaffolded site has zero findings in build, check
and validate, also with every rule promoted to error, and also with `--name/--lang de`.

## Decisions

- **Description** (npm `description` = `nera.starter.description`, a test keeps them equal): "A ready-to-edit Nera blog on @nera-static/theme-blog: three sample posts, tags, an archive by year, prev/next, an Atom feed, a sitemap, code blocks, navigation, responsive images, social links and imprint and privacy placeholders. No JavaScript."
- **`files`**: `config`, `pages`, `theme`, `CHANGELOG.md`. The sample image lives in `theme/assets/images/` (as in the theme fixture), so no root `assets/` folder exists.
- **No `lang` in page frontmatter** (the fixture sets `lang: en`): pages follow `app.lang`, so `--lang de` relabels the whole site instead of leaving English-tagged pages behind. Every page keeps a `slug` for later translations.
- **`translations.en` carries every theme, footer-link and plugin key with its English text** (identity), grouped with comments as in the fixture. This way `--lang <code>` copies a complete list to translate, the same idea as starter-blank's layout labels.
- **Home `title: Welcome`**, not the site name: `--name` only edits `config/app.yaml`, so a title equal to the sample name would have stayed "My Nera Blog" on a `--name` site. The `<title>` becomes "Welcome – <name>".
- **Sample name `My Nera Blog`.**
- **`images.yaml` `og: false` kept**, even with `origin` set: the theme writes no `og:image` tag (its `head-extra` seam is empty), so the 1200×630 crop would be generated and never referenced. A site that wants Open Graph adds a `head-extra.pug` override and turns `og` back on.
- **`code-blocks.yaml` is minimal** (`copy_button: false` plus its comment), as in the fixture. The published full config (`npx nera-code-blocks`) was not shipped, so the plugin's defaults stay the plugin's.
- **`fontawesome-cdn-link.pug` is not shipped**, although `npx nera-social-media-links` publishes it: it loads a CDN (§S6.5) and the fixture leaves it out too. The other vendor files are byte-identical to the publishers' output.
- **No `feed.yaml` / `sitemap.yaml`**: the defaults (Atom, `pages/post.pug`, 20 entries; all pages, `robots.txt`) fit.
- **`tag_overview_meta.description: All posts with this tag.`** in `config/tags.yaml`. Without it, tag pages have no `<meta name="description">`.
- **Social placeholder**: `Mastodon → https://example.com/@your-name`, with no icon (text label only).
- **`.gitignore` unchanged**: tests scaffold and build in `os.tmpdir()` and leave nothing in the repo.
- **Tests**: no `vitest.config.js` (as starter-blank); per-test/hook 180 s timeouts. Beyond the brief they also check that every root-relative `href`/`src` in the built site resolves, that the archive has two year groups, that no copy button renders, and that the README's German block builds clean.
- **`--lang de` finding**: with `--name "Brot & Zeit" --lang de`, `config/app.yaml` gets `de:` as a copy of `en:` (including `language_name: English`) and `en:` stays. The site builds, checks and validates with zero findings, but every page renders a one-item language switch whose only entry is the current language, labelled with the copied English name:
  ```html
  <nav class="lang-switch" aria-label="Language">
    <ul class="lang-switch__list">
      <li class="lang-switch__item"><span class="lang-switch__link" aria-current="true" lang="de">English</span></li>
    </ul>
  </nav>
  ```
  There is no `en` page to link (pages have no `lang`), so the theme leaves `en` out. This repo cannot prevent it without overriding the theme's contract partial `partials/lang-switch.pug`. That copy would be frozen into every site (no update path), so I did not ship one. Instead, the README's "German texts for `--lang de`" section gives the full `de:` block and says to delete the `en:` entry for a German-only blog. A test applies exactly that and asserts German output, no switch and zero findings. The real fix is in theme-blog (Carry-forwards).

## Carry-forwards

- **nera-theme-blog `views/partials/lang-switch.pug`** — render the switch only when `themeBlog.languageLinks(...)` returns two or more entries; today `app.translations` with two keys is enough, which gives the one-item switch above on every `nera new --starter blog --lang de` site. Reason: other repo.
- **nera-cli `src/starters.js`** — add the `blog` entry to `BUNDLED_STARTERS` (exact entry under Decisions) once 1.0.0 is on npm. Optionally, in `addLangTranslations`, consider *renaming* the entry instead of copying it when the starter's `translations` has a single language. Reason: other repo.
- **nera-plugin-tags `views/pages/tag-overview.pug`** — the item date is `new Date(page.meta.createdAt).toLocaleString(lang)`, with a time and in the build machine's time zone, and without `datetime`. Built with `TZ=America/New_York`, the starter's tag page shows `9/20/2026, 8:00:00 PM` for a post dated 2026-09-21 (UTC builds show `9/21/2026, 12:00:00 AM`). Proposed: `toLocaleDateString(lang, { year: 'numeric', month: 'long', day: 'numeric', timeZone: 'UTC' })` in a `time(datetime=…)`. After that release, regenerate this starter's `theme/views/vendor/plugin-tags/` (the starter ships the published copy unchanged). Reason: other repo.
- **nera-plugin-sitemap** — `<lastmod>` reads `lastmod`, `updatedAt`, `date`, but not `updated`, the key theme-blog and plugin-feed use. The starter's `posts/tags.html` (`updated: 2026-01-12`) is listed with `<lastmod>2025-11-04</lastmod>`. Reason: other repo.
- **nera-cli `template/theme/assets/.gitkeep`** — it is copied into every built site as `public/.gitkeep` (seen here too). Harmless, but core or the template could skip it. Reason: other repo.
- **Release** — merge, the hand-published 1.0.0, then a CI 1.0.1 within ~2 days; ROADMAP-ai.md L5 / "Slice 5 — progress"; `--starter blog` in the CLI template's `AGENTS.md`, the skill and the nera.js.org CLI page; `../generator/scripts/fleet-check.sh --fix nera-starter-blog`. ## Review hints

- **The lang-switch decision**: whether to ship a site-level `partials/lang-switch.pug` override after all (it would make `--lang de` clean out of the box, at the price of a frozen copy of a contract partial). I chose the README workaround plus a theme fix.
- **README length** (about 95 lines, printed in the terminal after `nera new`): the German block is about 20 of them. "First steps" is last, as in starter-blank, so it stands directly above the CLI's own next steps.
- **Sample post wording** in `pages/posts/*.md` (claims about plugin behaviour: full-text feed, responsive images in AVIF/WebP, `robots.txt`). I checked each against the build output and plugin READMEs, but they are what a new user reads first.
- **`privacy.md`** says that, as shipped, the blog stores nothing on the device "so no consent under § 25 TDDDG is needed for it". This is the same claim as the theme fixture, scoped to the shipped state, and the page is clearly marked as a placeholder.
- **The strict validate config** is embedded in `test/scaffold.test.js` (21 rules) rather than copied from the fixture at test time. If `nera check` gains a rule, add it there.
